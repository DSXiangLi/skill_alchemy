# 技能构建方案

## 输入门禁

技能构建是独立的第二层蒸馏。只有第一层行动指南、错误模式、重复要求、冲突要求和关联发现全部通过完整性检查后，才能开始。

## 构建流程

1. 读取第一层产物及其 session/turn 证据。
2. 按触发时机聚类，而不是按单次事故或项目名称聚类。
3. 搜索已有 `skills/` 和 AGENTS.md，判断规则是否已经存在。
4. 优先增强触发条件、执行步骤或通过标准相近的已有技能。
5. 只有在触发场景和检查职责均独立时才创建新技能。
6. 使用 `skill-creator` 技能按最佳实践构建或更新技能。
7. 运行 `quick_validate.py`，并在可用时运行 `skill_health_check` 或等价检查。

## 技能内容边界

`SKILL.md` 保留：

- 简洁、可区分的触发描述；
- 工作流步骤及步骤间关系；
- 必要的阻断条件；
- 脚本调用方式与预期输出；
- 详细 reference 的读取入口。

详细字段 schema、长示例、单步骤操作细节放入 `references/`；确定性校验、批处理和模板组装放入 `scripts/`。

不要把版本历史、实验过程、单次事故叙述或重复的“为什么”写入技能正文。

## 决策输出

每个规则聚类必须得到以下三种结论之一：

| 结论 | 必需信息 |
|---|---|
| 更新已有技能 | 目标技能、触发变化、步骤变化、通过/失败标准变化 |
| 创建新技能 | 唯一触发场景、职责边界、与现有技能的差异 |
| 不生成技能 | 应进入项目知识或被动规则的原因 |

## 验收标准

- description 主要描述何时触发，简洁且不罗列实现细节。
- 技能没有环境绑定绝对路径。
- 每个确定性检查尽量由脚本执行。
- QA 分布在对应阶段，并标明阻断式或建议式。
- 新增文件均被 `SKILL.md` 或运行时脚本引用，不产生僵尸文件。
- 技能健康检查无阻断问题后才能标记可用。
