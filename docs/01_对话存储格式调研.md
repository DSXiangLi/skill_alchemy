# 三大 CLI 工具历史对话存储格式调研

> 调研日期：2026-08-30
> 调研目标：全面了解 Kimi Code、Codex CLI、Claude Code 三款工具的会话存储方式，为后续对话提取与压缩提炼奠定基础。

## 一、Kimi Code CLI

### 1.1 存储根目录

```
~/.kimi-code/
├── sessions/                  ← 会话存储核心目录
│   └── <workspace_id>/
│       └── session_<uuid>/
│           ├── state.json     ← 会话元状态
│           ├── agents/
│           │   ├── main/wire.jsonl      ← 主 agent 对话日志（JSONL）
│           │   ├── agent-0/wire.jsonl   ← 子 agent 对话日志
│           │   └── main/tasks/         ← 后台任务输出
│           └── logs/kimi-code.log
├── session_index.jsonl       ← 全局会话索引
├── user-history/             ← 用户输入自动补全历史
├── workspaces.json           ← 工作区注册表
├── search-index/             ← 全文搜索索引
├── cache/                    ← query-store（分片）+ client-configs
├── config.toml               ← 模型/provider 配置
└── tui.toml                  ← TUI 配置
```

- **workspace_id** 格式：`wd_<目录名>_<12位hash>`，如 `wd_turtle_skill_1e23012d1461`
- **session_id** 格式：`session_<uuid4>`
- `workspaces.json` 中维护 workspace_id → 真实路径的映射

### 1.2 文件格式

#### state.json — 会话级状态

单 JSON 对象，记录会话元信息：

```json
{
  "id": "session_<uuid>",
  "version": 2,
  "cwd": "/home/lixiang/Desktop/project",
  "createdAt": 1787648950438,       // Unix 毫秒时间戳
  "updatedAt": 1787658806521,
  "archived": false,
  "agents": {
    "main": { "homedir": "...", "type": "main" },
    "agent-0": { "homedir": "...", "type": "sub", "parentAgentId": "main" }
  },
  "lastPrompt": "<用户最后一条输入>",
  "title": "<会话标题>",
  "lastTurnReason": "completed"
}
```

#### wire.jsonl — 对话核心日志（唯一事实来源）

JSONL 格式，append-only，协议版本 1.5。每行一个 JSON 事件。

### 1.3 事件类型全景

| 事件 `type` | 作用 |
|---|---|
| `metadata` | 协议版本 + 创建时间（文件首行） |
| `runtime.set_binding` | 绑定 workspaceId/runtimeId/agentId |
| `profile.bind` | 绑定模型别名、thinkingEffort、**完整 systemPrompt** |
| `permission.set_mode` | 权限模式 |
| `prompt.accepted` | 用户提交 prompt（含 promptId） |
| `turn.prompt` | 一轮对话开始，含 `input` 数组 + `origin.kind` |
| `context.append_message` | 追加一条**持久化消息**到上下文 |
| `context.append_loop_event` | **对话循环事件**（核心内容载体） |
| `llm.request` | 单次 LLM 请求元数据 |
| `usage.record` | token 用量 |
| `turn.ended` | 一轮结束（reason=completed/interrupted） |

### 1.4 对话轮次组织

一轮（turn）= 用户输入 → 多个 step（LLM 推理步）→ turn 结束：

```
turn.prompt (origin=user)
context.append_message (role=user)
  └─ step.begin (step=1)
       llm.request / usage.record
       content.part [think]     ← 思考
       content.part [text]      ← 可见文本
       tool.call (name, args)   ← 工具调用
       tool.result (output)     ← 工具结果
     step.end (finishReason=tool_use)  → 继续下一个 step
  └─ step.begin (step=2) → ... → step.end (finishReason=end_turn) → 本轮结束
turn.ended (reason=completed)
```

`step.end` 的 `finishReason`：
- `tool_use` → 工具执行后开启新 step，循环继续
- `end_turn` → 本轮结束

### 1.5 关键区分机制

#### assistant 消息不通过 `context.append_message` 持久化

`context.append_message` 全部是 `role=user`（来源：user/injection/task）。assistant 输出**仅以 loop event 形式**存在于 wire.jsonl 中。

#### `context.append_message` 的 `origin.kind`

| `origin.kind` | 含义 |
|---|---|
| `user` | 真实用户输入 |
| `injection` | 系统注入的 user-role 消息（todo_list_reminder / interruption / agents_md） |
| `task` | 后台任务完成通知 |

#### loop event 内部用 `event.type` 区分内容类型

| `event.type` | 作用 | 关键字段 |
|---|---|---|
| `step.begin` | 步开始 | `uuid`, `turnId`, `step` |
| `content.part` | 一段内容 | `part.type`: `think` / `text` |
| `tool.call` | 工具调用 | `toolCallId`, `name`, `args` |
| `tool.result` | 工具结果 | `parentUuid`, `toolCallId`, `result.output` |
| `step.end` | 步结束 | `finishReason`, `usage` |

#### thinking vs 可见文本

通过 `content.part` 事件的 `part.type` 字段区分：
- `think` → 思考内容，存于 `part.think`
- `text` → 可见文本（给用户看的话），存于 `part.text`

### 1.6 最终答案标记

**没有显式 final answer 标记。** 通过以下组合隐式表达：
1. `step.end` 且 `finishReason=end_turn`
2. 该 step 的最后一个 `content.part`（`part.type=text`）即最终回答
3. 随后 `turn.ended`（`reason=completed`）正式收尾

### 1.7 子 agent 存储

- 子 agent 在 `state.json` 中 `type:"sub"`，`parentAgentId:"main"`
- 有独立 `wire.jsonl`，格式与 main 完全一致
- 主 agent 通过 Agent 工具调用派生，结果以 `tool.result` 返回

## 二、OpenAI Codex CLI

### 2.1 基本信息

- 版本：`codex-cli 0.150.1`
- 主目录：`~/.codex/`（`$CODEX_HOME`）

### 2.2 目录结构

```
~/.codex/
├── config.toml                # 主配置
├── history.jsonl              # 用户输入历史（379条）
├── session_index.jsonl        # 会话索引
├── sessions/                  # ★ 会话存储主目录
│   └── YYYY/MM/DD/
│       └── rollout-YYYY-MM-DDTHH-MM-SS-{UUID}.jsonl
├── state_5.sqlite             # ★ 线程元数据索引库
├── thread_history_1.sqlite    # ★ 会话内容投影库
├── logs_2.sqlite              # 系统日志库
├── memories_1.sqlite           # 记忆库
├── goals_1.sqlite              # 目标库
├── queue_1.sqlite              # 任务队列库
├── shell_snapshots/            # Shell 环境快照
├── skills/ rules/ log/
└── responses_bridge.py litellm_config.yaml
```

### 2.3 会话文件

#### 命名规则

```
rollout-2026-08-28T13-38-50-01a046e0-c2b9-7851-a405-86c91edc6d0b.jsonl
└──┬─┘ └──┬──────────────────┘ └──┬────────────────────────────────┘
 前缀   ISO时间戳(本地)            会话UUID (v7, 时间排序)
```

#### 目录结构：按日期分层

```
sessions/YYYY/MM/DD/rollout-*.jsonl
```

- 格式：JSONL（每行一个 JSON 对象）
- **一个文件 = 一个 session**，可包含多个对话轮次
- 共 57 个会话文件，跨越 2026-07-14 至 2026-08-28

### 2.4 JSONL 行级结构

每行 JSON 公共字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `timestamp` | string (ISO 8601) | 写入时间 |
| `ordinal` | integer | 行序号（byte offset 索引） |
| `type` | string | 行类型 |
| `payload` | object | 负载内容 |

### 2.5 行类型

| 行类型 | 说明 |
|--------|------|
| `session_meta` | 会话元数据（文件首行） |
| `turn_context` | 轮次上下文 |
| `world_state` | 世界状态快照 |
| `response_item` | ★ 对话内容和工具调用的核心载体 |
| `event_msg` | 事件消息（状态变更、token统计等） |

### 2.6 response_item 子类型

#### `message` — 对话消息

通过 `role` 区分角色：

```jsonc
{
  "type": "message",
  "id": "msg_xxx",
  "role": "assistant",          // "user" | "developer" | "assistant"
  "content": [
    {
      "type": "output_text",    // assistant → "output_text"; user/developer → "input_text"
      "text": "已完成八项检查..."
    }
  ]
}
```

- `role: "developer"` — 系统指令注入
- `role: "user"` — 用户输入 + 环境上下文
- `role: "assistant"` — AI 回复

#### `reasoning` — 思考/推理

```jsonc
{
  "type": "reasoning",
  "id": "msg_xxx",
  "summary": [
    { "type": "summary_text", "text": "用户要求我检查..." }
  ],
  "content": null,
  "encrypted_content": null
}
```

推理内容存储在 `summary` 数组中（`summary_text` 类型），**明文**可读。

#### `function_call` — 工具调用

```jsonc
{
  "type": "function_call",
  "id": "msg_xxx",
  "name": "exec_command",
  "arguments": "{\"cmd\": \"ls /path\"}",
  "call_id": "call_xxx"
}
```

#### `function_call_output` — 工具调用结果

```jsonc
{
  "type": "function_call_output",
  "id": "fco_xxx",
  "call_id": "call_xxx",       // 关联到 function_call
  "output": "Chunk ID: a803f8\n..."
}
```

### 2.7 event_msg 事件

| payload.type | 说明 |
|--------------|------|
| `task_started` | 轮次开始（含 turn_id） |
| `item_completed` | 一个 item 完成事件（冗余但更结构化） |
| `token_count` | token 使用统计 |
| `task_complete` | ★ 轮次结束，含 `last_agent_message`（最终答案完整文本） |

### 2.8 对话轮次组织

```
[event_msg: task_started]           ← 轮次开始
  [response_item: message(role=developer)]  ← 系统指令
  [response_item: message(role=user)]       ← 用户输入
  [response_item: reasoning]                ← AI 思考
  [response_item: function_call]            ← 工具调用
  [event_msg: item_completed]               ← 工具完成
  [response_item: function_call_output]     ← 工具输出
  ... (推理 → 工具调用 → 输出 循环)
  [response_item: message(role=assistant)]  ← 最终回复
[event_msg: task_complete]          ← 轮次结束 (含 last_agent_message)
```

### 2.9 最终答案标记

**有显式标记：** `event_msg:task_complete` 的 `last_agent_message` 字段直接内嵌该轮次的最终答案完整文本。这是提取最终回答最简单的方式。

### 2.10 双层存储架构

Codex 采用 **"append-only JSONL + SQLite 投影"** 双层架构：

1. **写入层（rollout JSONL）**：所有事件追加写入，唯一事实来源
2. **查询层（SQLite）**：从 JSONL 异步投影解析，用于快速查询

#### state_5.sqlite — `threads` 表

| 字段 | 说明 |
|------|------|
| `id` | 线程 UUID |
| `rollout_path` | JSONL 文件绝对路径 |
| `created_at` / `updated_at` | Unix 时间戳 |
| `title` / `first_user_message` / `preview` | 会话标题/首条消息/预览 |
| `cwd` | 工作目录 |
| `git_sha` / `git_branch` | Git 信息 |

#### thread_history_1.sqlite — `thread_items` 表

| 字段 | 说明 |
|------|------|
| `thread_id` / `turn_id` / `item_id` | 三级 ID |
| `rollout_ordinal` | JSONL 行号 |
| `item_json` | 完整 item JSON |
| `item_type` | 类型枚举 |

`item_type` 统计：`commandExecution` 3733 / `agentMessage` 3189 / `reasoning` 2512 / `fileChange` 873 / `userMessage` 260

#### thread_history_1.sqlite — `thread_turns` 表

| 字段 | 说明 |
|------|------|
| `thread_id` / `turn_id` | 关联键 |
| `status` | "completed" / "interrupted" |
| `first_user_item_id` | 首条用户消息 ID |
| `final_agent_item_id` | ★ 最终 AI 回复 ID |
| `rollout_byte_offset` | 字节偏移（分页读取） |

## 三、Claude Code CLI

### 3.1 存储根目录

```
~/.claude/
├── projects/              ← 【核心】按项目分组的会话 JSONL 文件
├── session-data/          ← 会话摘要临时文件（350个 *.tmp）
├── session-env/           ← 会话环境快照
├── tasks/                 ← 任务进度跟踪
├── file-history/          ← 文件编辑历史快照
├── shell-snapshots/       ← Shell 环境快照
├── plans/ paste-cache/ plugins/ skills/ rules/ agents/
├── history.jsonl          ← shell 命令历史（6278行，非对话）
├── settings.json / settings.local.json
└── CLAUDE.md
```

### 3.2 会话文件

#### 目录命名规则

项目路径的绝对路径，将 `/` 替换为 `-`：
- `/home/lixiang/Desktop/project` → `-home-lixiang-Desktop-project`

#### 文件命名

每个会话是一个独立文件：`<session-uuid>.jsonl`（UUID v4）

项目目录可能还包含同名子目录存放外部化的 tool 结果：
```
projects/-home-lixiang-Desktop/
├── <uuid>.jsonl
└── <uuid>/
    └── tool-results/      ← 大输出外部存储
        ├── bt636y76c.txt
        └── bcrg9ok8v.txt
```

### 3.3 文件格式

JSONL，每行一个 JSON 对象，类型由顶层 `type` 字段区分。

#### 所有 `type` 值

| type | 数量 | 说明 |
|------|------|------|
| `attachment` | 6435 | 附加事件（hook 错误、中断通知等） |
| `assistant` | 1221 | 助手回复（thinking/tool_use/text 块） |
| `user` | 785 | 用户消息或 tool_result 回传 |
| `permission-mode` | 513 | 权限模式切换 |
| `ai-title` | 502 | AI 生成标题 |
| `last-prompt` | 501 | 最近用户提示快照 |
| `system` | 320 | 系统事件（API 错误等） |
| `file-history-snapshot` | 231 | 文件编辑历史 |

### 3.4 消息结构

#### `user` 消息

```jsonc
{
  "type": "user",
  "uuid": "5537abf7-…",
  "parentUuid": "…",          // 链接上一条记录
  "sessionId": "0aaae9e8-…",
  "timestamp": "2026-07-17T03:21:58.198Z",
  "message": {
    "role": "user",
    "content": "纯文本字符串 或 [内容块数组]"
  }
}
```

- 纯用户输入：`content` 是字符串
- 工具结果回传：`content` 是数组，含 `{ "type":"tool_result", "tool_use_id":"toolu_…", "content":"…" }`

#### `assistant` 消息

```jsonc
{
  "type": "assistant",
  "uuid": "…", "parentUuid": "…",
  "message": {
    "role": "assistant",
    "model": "glm-5.1",
    "stop_reason": null,       // 本数据集中多为 null
    "content": [ /* 内容块数组 */ ]
  }
}
```

`content` 块的三种类型：

| 块类型 | 结构 | 说明 |
|--------|------|------|
| `thinking` | `{ "type":"thinking", "thinking":"…", "signature":"…" }` | 推理过程 |
| `tool_use` | `{ "type":"tool_use", "id":"toolu_…", "name":"Read", "input":{…} }` | 工具调用 |
| `text` | `{ "type":"text", "text":"…" }` | 面向用户的文本回复 |

一条 assistant 消息通常只含**单一类型**的块（thinking/tool_use/text 各自为独立的 assistant 行）。

### 3.5 对话轮次组织

- 每条记录是独立 JSON 行，顺序追加写入
- **轮次链接靠 `parentUuid`**：形成消息链
- 典型一轮：`user(prompt) → assistant(thinking) → assistant(tool_use) → user(tool_result) → … → assistant(text)`

### 3.6 最终答案标记

**没有专门的 final-answer 标记。** 最终回复是一条 `assistant` 消息，其 `content` 数组含 `{ "type":"text" }` 块。判定方法：
- 解析每条 `type=="assistant"` 行
- 检查 `message.content[]` 中是否存在 `type=="text"` 块
- `stop_reason` 在本数据集中全为 null，不可靠

### 3.7 大输出外部化

当工具输出过大（>29.7KB），tool_result 的 `content` 用占位符存储，指向外部 `.txt` 文件：

```jsonc
{
  "type":"tool_result", "tool_use_id":"toolu_…",
  "content":"<persisted-output>\nOutput too large (29.7KB). Full output saved to: "
            "/home/lixiang/.claude/projects/.../tool-results/bt636y76c.txt\n\nPreview (first 2KB):\n…"
}
```

## 四、三工具横向对比

| 维度 | Kimi Code | Codex CLI | Claude Code |
|------|-----------|-----------|-------------|
| **存储根目录** | `~/.kimi-code/` | `~/.codex/` | `~/.claude/` |
| **核心格式** | JSONL (wire.jsonl) | JSONL (rollout) + SQLite | JSONL |
| **目录结构** | `sessions/wd_<id>/session_<uuid>/agents/<main\|agent-N>/` | `sessions/YYYY/MM/DD/rollout-*.jsonl` | `projects/<路径编码>/<uuid>.jsonl` |
| **会话文件命名** | session UUID | rollout-时间戳-UUID | session UUID |
| **对话组织** | turn → step → content.part/tool.call | turn → response_item + event_msg | parentUuid 链表 |
| **user 消息** | `context.append_message` (role=user, origin.kind=user) | `response_item` (type=message, role=user) | `type:user` 行 |
| **assistant 消息** | loop event (content.part type=text) | `response_item` (type=message, role=assistant) | `type:assistant` 行 (content含text块) |
| **thinking** | `content.part` (part.type=think) | `response_item` (type=reasoning, summary数组) | assistant content (type=thinking) |
| **tool 调用** | `tool.call` + `tool.result` (parentUuid配对) | `function_call` + `function_call_output` (call_id配对) | assistant content (type=tool_use) + user content (type=tool_result) |
| **最终答案** | 隐式：step.end finishReason=end_turn 前的 text part | **显式**：event_msg:task_complete.last_agent_message | 隐式：assistant content含text块 |
| **子 agent** | 独立 wire.jsonl (agents/agent-N/) | 独立 thread (rollout 文件) | isSidechain 标记 |
| **辅助索引** | session_index.jsonl + search-index | state_5.sqlite + thread_history_1.sqlite | session-data/*.tmp + tasks/ |
| **大输出外部化** | tasks/<id>/output.log | 内联 | tool-results/*.txt |

### 4.1 提取难度排序

1. **Codex（最简单）**：`event_msg:task_complete.last_agent_message` 直接给出最终答案文本；SQLite 中 `thread_turns` 表的 `first_user_item_id` / `final_agent_item_id` 提供精确指针
2. **Kimi Code（中等）**：需遍历 loop events，找 `finishReason=end_turn` 的 step 中的 text content.part
3. **Claude Code（中等）**：需遍历 assistant 行，找 content 含 text 块的记录；依赖 parentUuid 链重建轮次

### 4.2 共性发现

1. **三者均为 JSONL 格式** — append-only，每行一个 JSON 事件
2. **thinking/推理均明文存储** — 可直接读取
3. **tool 调用与结果均配对存储** — 通过 ID 关联
4. **user 消息均可通过角色字段识别** — 但需区分真实用户输入与系统注入/工具结果回传
5. **最终答案提取方式各异** — Codex 最友好，另两者需隐式推断
