# 关联分析与两层蒸馏方法

## 核心原则

Skill Alchemy 只保留关联分析路径。它不先用关键词筛选“纠正”，也不将所有 session 拆成互不相关的固定批次。

默认取最近 10 个 session 作为锚点。用户可以根据 session 长度和主题密度指定其他正整数 `last-n`；当请求数量超过可用 session 数时，使用全部可用 session 并明确报告实际数量。

## 七阶段流程

1. **提取**：把四种 CLI session 转换成统一 JSONL，并固化 session 时间。
2. **锚定**：按时间排序，生成 last-n 锚点、全量索引和本次分析指令。
3. **锚点语义分析**：识别真正纠正和有效指引，以前后行为变化作为证据。
4. **关联搜索**：由 AI 从锚点发现中推导搜索目标，回查历史 session。
5. **归纳**：聚类、去重并区分通用规则、项目知识、错误模式和冲突要求。
6. **第一层蒸馏**：输出证据化分析产物并通过完整性检查。
7. **第二层技能合成**：基于第一层产物更新已有技能或创建新技能。

## Session 边界

锚点文件中的每个 session 必须具有：

- `BEGIN_SESSION id=...`；
- 包含相同 `session_id` 的标题；
- `source_tool`、`source_file`、project、turn 数等元数据；
- `END_SESSION id=...`。

同项目的相邻 session 仍然是不同证据单元。跨 session 结论必须分别引用 session id 和 turn id，再说明两者的关联。

## 纠正分类

| 类型 | 判定 | 提取 |
|---|---|---|
| 真正纠正 | AI 原行为错误，用户指出后方向发生变化 | 是 |
| 有效指引 | 用户增加了 AI 未考虑的约束，AI 随后采用 | 是 |
| 冗余确认 | AI 原本已按该方向执行 | 否 |
| 单纯推进 | “继续”“下一步”等未增加约束 | 否 |

关键词只能用于定位候选历史文本，不能代替语义分类。

## 关联维度

1. **历史根因回溯**：定位问题最初引入的 session，判断编码时能否预防。
2. **关联模块与项目**：检查同类问题是否存在于兄弟模块、适配器、UI 路径或其他项目。
3. **模式和优化扩散**：判断修复、抽象或验证方法是否应推广。
4. **重复要求验证**：仅当用户重复约束且 AI 在两次之间确实违反或遗漏时提取。
5. **规则与技能有效性**：检查已有 AGENTS.md 或技能是否已经覆盖但缺乏可执行门禁。

## 分层 QA

- Phase 1 后：检查统一字段、session 唯一性和时间戳。
- Phase 2 后：运行 `scripts/validate_run.py`，边界或索引不一致时阻断分析。
- Phase 3 后：每条提取项必须具有前后行为证据，否则删除。
- Phase 4 后：每条跨 session 关联必须分别引用来源，不得合并证据。
- Phase 5 后：检查重复项、项目特定项和冲突要求是否正确分流。
- Phase 6 后：运行第一层产物完整性检查；缺少必需类别时阻断技能合成。
- Phase 7 后：运行 `skill-creator` 的验证器以及可用的技能健康检查。
