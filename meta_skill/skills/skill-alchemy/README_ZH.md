# Skill Alchemy（技能炼金术）

> 从原始对话中提炼可执行技能——不是被动规则。

Skill Alchemy 从本地 AI 对话历史中提取用户纠正和重复错误，跨 session 做关联分析，再把有证据支撑的发现转化为技能更新。

你每天都在跟 AI 聊天写代码，对话记录堆成山。Skill Alchemy 就是从这些"废矿"里提炼出"金子"——那些你反复纠正 AI 的经验——然后锻造成带检查清单、grep 命令和通过/失败标准的技能。技能会在关键时刻主动触发，而不是像规则一样被动躺在文件里。

位于 [Memory Curator](#与-memory-curator-的关系) 之上。Curator 管理记忆文件；Alchemy 从原始对话中炼金。

---

## 为什么需要它

你一定有过这种感觉：**AI 在不同 session 中犯同样的错。**

上周你跟它说"改完要启动服务测试"，这周它又只跑了 pytest 就说"完成了"。上个月你纠正"不要顺手改无关代码"，这个月它改 A 顺手又把 B/C/D 也改了。

你纠正了，AI 当时听了，下次对话全忘了——因为每次新 session 都是白纸一张。

你可能会想写进 AGENTS.md，但写进去就够了吗？我们验证过：**88 个 session 中，用户反复要求"启动服务真实验证"——而这条规则已经写在 AGENTS.md 里了。** 规则存在，AI 依然不遵守。

原因很简单：**"应该做"不等于"会做"。** AGENTS.md 写的是"要验证"，但没写"什么时候触发、检查什么、怎么检查、什么算通过"。AI 读了规则，但不知道怎么执行。

Skill Alchemy 解决的就是这个断层——**把"应该做"变成"会做"。**

## 工作流程

当前只有一条分析路径，共七个阶段：

1. 将 session 提取为统一 JSONL。
2. 选择最近 session 作为锚点，默认 last10。
3. 通过语义判断识别真正纠正和有效指引。
4. 沿五个关联维度自主搜索相关历史。
5. 聚类、去重并泛化证据。
6. 生成第一层分析产物并通过完整性 QA。
7. 使用 `skill-creator` 合成或更新技能，再执行技能检查。

关键词可以用于历史文本候选定位，但不能用于判断某个用户 turn 是否属于纠正。

### 工作原理——逐阶段说明

**阶段一（提取）：** AI 每天的对话都存在本地硬盘上，但四种工具存的格式完全不同。`extract.py` 就是挖矿机——不管哪种格式，都挖出两样东西：**你问了什么**，**AI 最终回了什么**。工具调用、思考过程、系统注入，全部扔掉。为什么只要这两样？因为判断"AI 做对了还是做错了"，只需要看你的输入和 AI 的最终回答。中间过程是噪音。

**阶段二（选矿）：** 挖出来的矿有 3500+ 轮对话，直接给 AI 看太多了。`distill.py` 把它们组织成可读的批次。巧妙之处：不分析全部——**以当前工作为中心回溯历史。** 你在修一个 SSE 的 bug，它就去历史 session 里搜"SSE""compact""流式"，找到之前写 SSE 代码的 session，问能不能在编写时就避免这个 bug。

**阶段三（语义分析）：** 这是核心——**不用关键词匹配，让 AI 自己判断。** 我们一开始试过关键词。结果 39% 是误报：用户说"很好继续"被当成纠正；用户说"我认为应该用 B"被标记，但 AI 之前已经在用 B 了。现在 AI 通读对话，自己判断每轮用户输入属于哪类：

| 类型 | 含义 | 要不要提炼 |
|------|------|:---------:|
| **真正纠正** | AI 做错了，用户指出，AI 确实改了方向 | ✅ |
| **有效指引** | 用户给了 AI 没想到的方向，AI 采纳了 | ✅ |
| **冗余确认** | AI 本来就在做，用户只是确认 | ❌ |
| **纯推进** | "继续""下一步" | ❌ |

判断标准只有一个：**纠正前 AI 的行为 ≠ 纠正后 AI 的行为？** 变了才算真正纠正；没变说明 AI 本来就在做，不提取。

| 问题 | 关键词方案 | AI 语义理解方案 |
|------|-----------|---------------|
| 冗余确认未过滤 | "很好继续"被当成纠正 | AI 判断之前已做到，跳过 |
| 不含信号词的纠正被漏掉 | 不含"不对""应该"的纠正被漏 | AI 理解语义，不依赖关键词 |
| 上下文窗口固定 | 只看前后 1 轮 | AI 通读全文，理解长周期变化 |
| 无效果验证 | 只检查有没有上下文 | AI 对比前后行为方向是否实质变化 |

**阶段四（关联）：** 这是 Skill Alchemy 区别于"简单总结"的关键。AI 在分析 batch 内容时，如果发现某个问题可能和历史上其他 session 有关，**自主用 grep/read 工具去 `output/extracted/` 目录搜索更多历史 session**。搜什么、搜多深，完全由 AI 的语义理解决定，不受预定义关键词限制。

**阶段五（重复要求）：** 与阶段四类似，AI 自主搜索历史 session。但目的不同——阶段四是发现问题和优化的关联，阶段五是验证**同一个约束是否在多个 session 中被用户反复声明且 AI 确实犯了错**。三个条件同时满足：(1) 你在某轮中要求了某个约束，(2) 在后面的轮次或 session 中你又要求了同一件事，(3) 在两次之间，AI 确实犯了违反该约束的错。**只有 AI 确实犯了错才算数。**

**阶段六（锻造）：** 最后一步——把规则锻造成技能。规则说"应该验证再声称完成"。技能说：触发条件是当 AI 要说"完成了"时，检查服务是否启动（`curl http://localhost:port/health`），检查是否发了真实请求（不只是 pytest），检查 UI 改动是否看了实际渲染效果，检查改了 A 模块是否测了调用 A 的 B 模块，检查改完代码是否重启服务，检查测试 case 是否足够复杂。**全部 ✅ 才能说"完成"。** 规则被动存在，技能在关键时刻主动触发。

## 快速开始

在技能目录执行：

```bash
python3 scripts/extract.py \
  --tool all \
  --min-turns 3 \
  --output output/extracted \
  --format jsonl

python3 scripts/distill.py output/extracted -o output/run
```

默认锚点大小为 10。session 特别短、特别长或主题密度不同时，可以选择其他正整数：

```bash
python3 scripts/distill.py output/extracted -o output/run --recent 20
```

如果请求值超过可用 session 数，则使用全部可用 session；零和负数会被拒绝。

`distill.py` 会自动校验生成文件，也可以单独复跑：

```bash
python3 scripts/validate_run.py output/run
```

## 生成文件

组织阶段生成：

```text
output/run/
├── anchor_recent.md
├── session_index.md
└── ANALYSIS_INSTRUCTION.md
```

分析阶段分两层产出：

```text
output/run/
├── action-guides/
├── error-patterns/
├── repeated-requirements/
├── conflicting-requirements/
├── related-findings/
└── skill-synthesis/
```

前五个目录保存证据和分析；只有第一层通过完整性门禁后，才创建 `skill-synthesis/`。

技能合成前检查第一层产物：

```bash
python3 scripts/validate_run.py output/run --first-layer
```

## 关联维度

- 历史根因回溯；
- 关联模块和项目分析；
- 模式与优化扩散；
- 重复要求验证；
- 已有规则和技能有效性检查。

任何跨 session 结论都必须分别引用来源 session 和 turn。项目名称相似不能作为合并 session 的依据。

### 详细说明与真实案例

孤立地看每个 session 只能得到孤立的教训。AI 自主关联 session 之间的关系，能发现更深层的模式：

#### 纵向追溯（向过去看）

AI 在当前 session 中发现一个 bug 修复，主动去历史 session 里搜索这个代码最初是谁写的。找到了就问：**编写时有没有信号可以避免这个 bug？** 如果有，提炼成"编码时预防指南"。

真实案例：一个"工具名重复"bug（bash 变成 bashbash）。根因是 LangChain 的 `merge_dicts` 本身就会拼接字符串字段，但实现者又用 `+=` 拼了一次。如果编写时读了上游 merge 逻辑（5 分钟），这个 bug 永远不会发生。但实际上同一个类 bug 在 4 个不同模块反复出现，修了 30+ 个 session——一个 merge 语义审计就能预防全部。

#### 横向迁移（向旁边看）

AI 在当前 session 中发现 A 模块有个问题，主动搜索：**B 模块是不是也有同样的问题？** 同一个开发者写的代码有相似的 pattern，A 的 bug 很可能 B 也有。

真实案例："环境混淆"——SproutHarness 有 6 套独立的环境映射实现，每套都有不同的 bug。修了一个没修其他的，因为没人检查。

#### 优化扩散（向未来看）

AI 在当前 session 中发现一个优化方案，主动搜索：**这个优化方案能不能推广到其他模块？**

真实案例：一个 session 引入了 `normalize_env()` 作为统一环境检测函数。三个其他项目各自实现了自己的版本——如果 `normalize_env()` 被提升为共享工具，那些项目只需一行 import 而非多文件重构。

#### 重复要求验证

AI 从锚点 session 中识别用户提出的约束，然后自主用 grep 搜索全部历史 session 中是否也提到过同一约束，并验证 AI 是否确实犯了相关错误。

477 个 session 中，我们发现了 8 个高频重复要求：

| 反复要求的约束 | 重复 session 数 | AI 每次都犯错 | 已在 AGENTS.md？ |
|--------------|:------------:|:-----------:|:--------------:|
| 启动服务真实验证，别只跑 pytest | 88 | ✅ | ✅（但仍然违反） |
| 简化，别过度工程 | 30 | ✅ | ✅ |
| 先出方案再写代码 | 28 | ✅ | ✅ |
| 先定位问题再修复 | 23 | ✅ | ⚠️ 部分覆盖 |
| 只改我要求的，别扩展 | 23 | ✅ | ✅ |
| 确认环境（本地/测试/生产） | 34 | ✅ | ✅ |
| 提交前等用户确认 | 12 | ✅ | ✅ |
| 根因修复，别打补丁 | 3 | ✅ | ✅ |

**8 条全部已经写在 AGENTS.md 里了。AI 仍然反复违反。** 规则存在，但执行力度不够。这个维度不只是发现"AI 做错了什么"——它发现的是 **"AI 被纠正过但仍然做错了什么"**——对已有规则有效性的直接检验。

#### 已有规则和技能有效性检查

这个维度检查的是已写入 AGENTS.md 的规则或已有技能是否真的预防了它们所针对的错误。上面的重复要求表就是证据：8 条约束全部有 AGENTS.md 对应条目，AI 仍然跨 session 持续违反。这验证了核心论点——**写规则是必要的但不充分；规则需要被锻造成带触发条件、检查清单和通过/失败标准的可执行技能。**

最严重的案例（Session 242/243）：用户连说 3 次"不要提交仅检查"（第 6、7、8 轮），因为 AI 一直试图提交。

## 实验结果

我们跑了两轮实验验证方案的有效性。

### 第一轮：不同 session 数量对比（1 / 5 / 10）

**目标**：确定需要多少个 session 才能有效提炼，并对比关键词匹配 vs AI 语义理解。

**设置**：用 1、5、10 个 session 跨三种工具（Kimi Code、Codex、Claude Code）测试。三组都使用**标准模式**（全量分批分析）——即所有 session 都作为输入喂给 AI 分析。这与关联模式不同——关联模式下只有最近 N 个 session 作为锚点，其余按需搜索。

**这个实验实际测试的是**：**输入量**对原则质量的影响。它不测试关联搜索范围的影响——那是第二轮的实验目标。

#### 提取结果

| 指标 | 1 session | 5 session | 10 session |
|------|-----------|------------|------------|
| 总轮次 | 167 | 538 | 860 |
| 关键词匹配数 | 31 | 149 | 151 |
| AI 识别的真正纠正 | 35 | 52 | 73 |
| 关键词误报率 | ~39% | ~39% | ~39% |

> **说明**：关键词匹配数（31/149/151）来自早期的 `scan.py` 方案，该脚本已删除。AI 识别的纠正数（35/52/73）来自子 agent 读取 batch 文件分析。重跑可能略有浮动，但比例关系（AI 语义分析 < 关键词匹配，因为过滤了误报）和核心结论不变。

**关键发现**：AI 语义分析稳定过滤掉约 39% 的误报，同时发现了不含任何信号词的真正纠正。

#### 不同规模的产出

| 规模 | 纠正类型覆盖 | 指南通用性 | 推荐 |
|------|:----------:|:---------:|------|
| 1 session | 4/6 类 | 项目特异化，不可泛化 | 仅测试用 |
| **5 session** | **5/6 类** | **可跨项目泛化** | **甜区** |
| 10 session | 5/6 类 | 相比 5 略有提升 | 边际递减 |

**5 个 session 是甜区**——足够覆盖多个项目和工具、多种纠正类型，但不会因为数据量太大导致分析冗余。

#### 窗口大小不只是影响数量——它直接改变原则的质量

这一点经常被忽略：不同窗口大小产出的不是"更多或更少的原则"，而是**不同质量和性质的原则**。

| 维度 | 1 session | 5 session | 10 session |
|------|-----------|------------|------------|
| **纠正类型覆盖** | 4/6 种 | 5/6 种 | 5/6 种 |
| **原则通用性** | 全部来自单一项目，无法泛化 | 跨项目验证过，可泛化 | 与 5 持平 |
| **错误模式识别** | 只能看到"这次做错了" | 能看到"这个模式在多个项目重复" | 能确认"这个模式是系统性的" |
| **可操作性** | 偏向具体项目操作 | 提炼出跨场景可执行的检查清单 | 与 5 持平，边际递减 |
| **过度拟合风险** | 高——可能把项目特有约定当成通用原则 | 低——多项目交叉验证过滤了项目噪音 | 低，但新增信息有限 |

**核心发现**：1 个 session 提炼出的原则看似合理，但本质是过度拟合——它把"这个项目的特有约定"当成了"AI 的通用错误模式"。只有 5 个 session 以上的多项目交叉验证，才能区分"项目特定知识"和"通用行为指南"。而 10 个 session 相比 5 个的增量，主要是同类型项目的重复纠正，聚类后不产生新的原则条目。

#### 关键词漏掉的（AI 发现了）

1. "改完代码忘记重启服务"——无信号词，但 AI 语义理解抓到了
2. "命令不适应目标环境"（docker compose vs docker-compose）——无"不对"关键词
3. "给选项而非直接执行"——用户说"直接帮我部署，不要给选项"
4. "声称已汉化但只改了主文件"——无信号词
5. "做了功能但没接入产品入口"——无信号词
6. "核心目标偏移不自知"——渐进偏移，非单次纠正

#### 关键词误报的（AI 过滤了）

1. "很好请给出 progress 文档"——AI 本来在写文档，用户只是确认方向
2. "是的我认为 L1 和 L3 也需要存储"——AI 之前的方案已包含 L1/L3
3. "几个建议，图表可以放到 HTML"——AI 之前已提出类似方案
4. "继续，注意每步需要完整测试"——前半句是推进，后半句是约束

### 第二轮：关联分析（跨 Session 关联）

**目标**：测试跨 session 关联分析能否发现孤立分析遗漏的洞察。

**设置**：用最近 5 个 session 作为锚点，在 472 个历史 session 中按关键词和项目匹配搜索相关内容。AI 执行三维关联分析。

**与第一轮的关系**：第一轮测试的是"输入量对原则质量的影响"（标准模式，所有 session 都作为输入喂给 AI）。第二轮测试的是"关联搜索是否改变原则性质"（关联模式，只有 5 个 session 作为输入 + 历史 session 按需搜索）。关键区别在于：第一轮的 10-session 组把 10 个 session 全喂给 AI；第二轮只喂 5 个 session 但搜索 472 个历史 session 中的关联证据。后者更高效（输入更小 → token 成本更低）且更精准（搜索由当前工作上下文驱动，而非随机纳入）。

#### 为什么要做关联——原理分析

session 之间不是孤立的日志，它们存在三种结构性关联关系。利用这些关系，能发现单 session 分析永远无法发现的模式：

**时间关联（过去 → 现在）**：同一段代码的"编写 session"和"修复 session"之间存在因果关系。如果在编写时就预防了，后面的修复 session 根本不需要存在。这种关联能回答"这个 bug 能否在源头预防"——这是单 session 分析无法回答的，因为它需要同时看到编写和修复两个 session。

**空间关联（此处 → 彼处）**：同一个开发者、同一个项目、同一套架构模式下的不同模块，往往有相同的盲区。A 模块的 bug 很可能 B 模块也有。这种关联能回答"这个问题是否是系统性的"——单 session 只看到"修了 A"，看不到"B/C/D 是否也有同样的坑"。

**方案关联（此法 → 彼法）**：一个模块的优化方案、架构模式、验证方法，往往可以迁移到其他模块。这种关联能回答"这个优化能否推广"——单 session 只看到"在这个模块做了"，看不到"其他模块也可以用同样方法"。

这三种关联不是"多搜几个 session"——它是利用对话之间的**结构关系**来发现单 session 无法发现的模式。不关联就只能看到"这次发生了什么"；关联了才能看到"这个类问题在什么条件下会发生、如何系统性地预防"。

#### 纵向追溯发现

| Bug | 原始编写 session | 能否在编写时预防？ | 错过的信号 |
|-----|---------------|:----------------:|-----------|
| 工具名重复（bashbash） | 编写 merge 逻辑的 session | ✅ | LangChain `merge_dicts` 源码 |
| 长 bash 执行网络断连 | 实现 SSE 心跳的 session | ✅ | Git log 中已有的心跳修复记录 |
| Compact token 计数链 | 集成 compact hook 的 session | ✅ | State 回写集成缺口 |

**关键洞察**：3 个 bug 在编写时都有明确的预防信号。如果实现者多查一个东西（上游 merge 逻辑、git 历史、集成端点），bug 根本不会存在。

#### 横向迁移发现

| 系统性模式 | 受影响模块数 | 浪费的 session 数 |
|-----------|:----------:|:---------------:|
| 流式消息重复 | 4 个独立模块 | 30+ |
| 环境混淆 | 6 套独立实现 | 34+ |
| `finish_reason` 异常处理 | 5 个 session | 5+ |
| 修复复发（声称修好但又回来） | 4 个 bug | 12+ |

**关键洞察**：流式消息重复被当作 4 个独立事件处理。实际上它是一个病——merge 语义不充分。逐个修了 30 个 session 花了大量时间；如果第二次出现时就做一次 merge 语义审计，后面的都能预防。

#### 优化扩散发现

| 优化方案 | 来源 | 可推广到 |
|---------|------|---------|
| `normalize_env()` | SproutHarness session | ThinkSkillsHub、poster、image-studio、hermes |
| ContextVar 结构化日志 | SproutHarness session | poster、ThinkSkillsHub、hermes |
| Agent 效果测试协议 | SproutHarness session | poster、ThinkSkillsHub、mcp_checker |
| StreamBridge SSE 设计 | SproutHarness session | 钉钉适配器、Dify 插件 |
| 对话压缩管道 | 本项目（turtle_skill） | SproutHarness 记忆系统 |

**关键洞察**：对话压缩管道（本项目）正是 SproutHarness 记忆系统设计中缺失的自动化录入层。两者独立开发——关联分析揭示了它们应该被连接。

#### 关联分析 vs 独立分析的差异

| 维度 | 独立分析能看到 | 关联分析增量发现 |
|------|-------------|----------------|
| 问题频率 | 每个 session 各自的纠正 | Workspace bug 被报告 3 次才修；"补丁优先"跨 3 个项目重复——是系统性的，不是偶然的 |
| 架构相似性 | 各 session 技术问题看起来无关 | "双真相源"反模式在 3 个模块出现——一个教训能预防其他 |
| 验证方法链 | 用户在某个 session 要求的验证方法 | "真实案例复现""先方案后代码"在多个 session 中被反复要求——AI 不会自发做 |
| 技能动机 | AGENTS.md 规则各自存在 | "修复方案审核"技能的创建动机来自跨 session 的反复纠正——规则不是凭空写的 |
| 遗漏修复风险 | 只看到当前 session 的问题 | Session 21 识别了根因但没修——如果当时修了，Session 3 的 18 轮对话完全不需要 |

#### 关联模式对原则性质的根本改变

这一点必须强调：关联分析不只是"多发现几个问题"——它**改变了提炼出的原则本身的性质**。

同样的"补丁式修复"这个纠正，在独立分析中只是一条"AI 倾向于打补丁"的规则。但在关联分析中，当我们看到同一个模式在 3 个不同项目（SproutHarness、pptx-composer、poster）中被用户反复纠正，它从"某个 session 中的个别纠正"升级为**"AI 的系统性行为缺陷"**。

| 同一条原则 | 独立分析中的表述 | 关联分析后的表述 |
|-----------|----------------|----------------|
| 补丁式修复 | "AI 倾向于打补丁而非根因修复" | "AI 的补丁优先倾向是跨项目的系统性行为缺陷，用户为此专门创建了'修复方案审核'技能来约束——说明 AGENTS.md 规则力度不够" |
| 验收标准不足 | "AI 声称完成但实际有问题" | "AI 的验收降级在 88 个 session 中反复出现，即使 AGENTS.md 已有规则仍违反——需要更强的可执行门禁" |
| 流式消息重复 | "修复了流式消息重复 bug" | "同一个 merge 语义缺陷在 4 个独立模块重复出现 30+ 个 session，逐个修不如一次审计——这是一个 bug 类而非单个 bug" |

**核心发现**：关联分析让原则从"描述现象"升级为"揭示本质"。独立分析告诉你"AI 做错了什么"，关联分析告诉你"这个错误是系统性的还是偶然的、已有的规则是否有效、应该用技能还是规则来约束"。这种性质的改变直接影响产物的形态——是写一条被动规则，还是锻造一个带触发条件的可执行技能。

### 重复要求验证

重复要求维度在全部 477 个 session 上单独验证：

| 约束 | 搜索关键词 | 命中 session 数 | AI 犯错确认 | 高优先级？ |
|-----|----------|:-----------:|:-----------:|:---------:|

## 为什么比其他方案更有效

### vs 关键词匹配

关键词是我们的第一版方案，它两边都失败了：
- **39% 误报**："很好继续"和"我认为应该用 B"（AI 已经在用 B）被当成纠正
- **漏掉真正纠正**："改完忘重启服务"没有信号词，但确实是 AI 的失败

AI 语义理解两边都修了：理解上下文、对比前后行为、只提取真正改变了方向的纠正。

### vs 逐 session 独立分析

独立分析每个 session 只能得到孤立的教训。但它：
- 看不到同一个 bug 被报告 3 次才修
- 看不到同一个反模式在 4 个模块都存在
- 不能追溯 bug 到源头问"能不能预防"

跨 session 关联分析揭示了这些系统性模式——"修一个 bug"和"消灭一类 bug"的区别。

### vs 写 AGENTS.md 规则

AGENTS.md 规则必要但不充分。数据证明了这一点：
- 88 个 session 反复要求"启动服务真实验证"——规则已在 AGENTS.md
- 30 个 session 反复要求"简化"——规则已在 AGENTS.md
- 23 个 session 反复要求"只改要求的"——规则已在 AGENTS.md

规则说"应该"。技能说"怎么做"。规则是被动文本。技能是带 grep 命令、通过/失败标准、结构化报告的可执行检查清单，在正确时机触发。

**Skill Alchemy 的产出不是更多规则——是能执行规则的技能。**

### vs 人工创建技能

人工创建技能有效但：
- 慢——你得记住出了什么问题再写
- 不全——你只记得最近的事故，不是 30 个 session 中的模式
- 主观——你写的是最让你烦的，不是数据显示最高频的

Skill Alchemy 系统化处理 477 个 session，按频率聚类，按影响排序。生成的 4 个技能覆盖了 8 个最高频纠正模式的 100%。

## 技能覆盖

Skill Alchemy 运行后，产出的技能覆盖完整开发工作流：

```
需求收到 → simplification_gate（要不要做？能否更简单？）
         → change_scope_control（改哪些文件？确认范围）
         → fix_plan_review（方案是否合理？）
         → [实现阶段]
         → issue_triage_gate（遇到 bug？先诊断）
         → code_fix_acceptance（修复完成？规范验收）
         → pre_completion_gate（声称完成？过门禁）
         → pre_commit_doc_rescan（提交前？文档同步？用户授权？）
```

10 个技能，每个都有触发条件、可执行检查清单、grep 命令和通过/失败标准。覆盖 8 个最高频纠正模式的 100%，覆盖 AGENTS.md 指南的 96%。

**不需要再新增技能**——10 个技能已覆盖从"需求收到"到"提交完成"的完整链路。继续新建边际价值递减。

## 与 Memory Curator 的关系

```
Memory Curator（管家）              Skill Alchemy（炼金术士）
─────────────────────              ──────────────────────────────
管理记忆文件                         从原始对话中提炼金子
维护、清理、过期淘汰                 纠正 → 规则 → 可执行技能
"记忆文件是否健康？"                  "AI 是否真的在学习？"
日常运维                            周期性深度提炼
```

Curator 确保记忆文件不膨胀、不过期、格式正确。Alchemy 更深——读原始对话、识别 AI 反复犯的错、锻造成预防复发的技能。

两者在不同层工作：
- **Curator** = 文件系统管理（对记忆文件做 CRUD）
- **Alchemy** = 语义分析（对话教会了我们什么？）
